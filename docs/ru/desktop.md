# Профили Claude Desktop

[← README](../../README.ru.md) · [English](../desktop.md)

Всё выше — про CLI. У **десктопного приложения** та же проблема: одно приложение — один залогиненный аккаунт. И для неё нашлось чистое решение.

Приложение построено на Electron, а значит понимает ключ Chromium `--user-data-dir`. Указываем ему нашу директорию — и получаем полностью изолированный профиль: свой вход, свои настройки, свои MCP-серверы. Это тот же приём, что этот инструмент уже применяет для CLI через `CLAUDE_CONFIG_DIR`, — но с одним свойством, которого у CLI-аккаунтов нет:

> **Профили работают одновременно.** Никакого «переключения» нет. Рабочий и личный аккаунт могут быть открыты в двух окнах в один момент. Приложение не берёт single-instance-блокировку, а блокировка Chromium лежит внутри каждой профильной директории.

**Входить нужно при закрытом Claude.** Это не пожелание: вход завершается переходом по ссылке `claude://`, а её система отдаёт тому экземпляру, что зарегистрирован на схему, — и это не тот, который вход начинал. При другом открытом окне новый профиль её просто не получит. Поэтому:

1. Закройте Claude.
2. `claude-acc desktop add <имя>` и войдите в открывшемся окне.
3. Дальше открывайте сколько угодно профилей — они работают одновременно.

`desktop add` при запущенном Claude откажется и назовёт, что именно открыто, вместо того чтобы поднять окно, в котором вход не завершится. Та же проверка у `desktop run` для профиля, где вход ещё не выполнен; уже вошедший открывается свободно. `--force` её отключает.

```bash
claude-acc desktop add work      # создать профиль и открыть на нём Claude, чтобы войти
claude-acc desktop add work -s   # ...и сразу перенести MCP-серверы из профиля приложения
claude-acc desktop list          # профили и то, под каким аккаунтом каждый
claude-acc desktop usage         # ...плюс их живой расход лимитов 5ч / 7д
claude-acc desktop run work      # открыть Claude на этом профиле снова
claude-acc desktop clone-config work   # перенести MCP-серверы в существующий профиль
claude-acc desktop clone-runtime work  # склонировать ~10.5 ГБ рантайма — на APFS бесплатно
claude-acc desktop remove work   # удалить профиль целиком
```

`desktop add` создаёт `~/.claude-switch/desktop/<name>/` и открывает на нём приложение. Окно поднимется без входа — войдите там под тем аккаунтом, для которого профиль заводился:

```
$ claude-acc desktop add work
Профиль десктопа 'work' создан. Открываю Claude на нём...
Оно откроется без входа — войдите там под аккаунтом для этого профиля.
Профиль полностью изолирован, поэтому приложение заново скачает в него образы песочницы — это несколько ГБ.

Открыть его позже:  claude-acc desktop run work
```

```
$ claude-acc desktop list
Профили Claude Desktop:
    work  (вход не выполнен)
    ~/Library/…/Claude/  (собственный профиль приложения)
```

После входа в этой строке будет виден аккаунт — см. [`desktop usage`](#под-каким-аккаунтом-каждый-профиль-desktop-usage).

Последняя строка — собственный профиль приложения, тот самый, что открывается из Dock. Мы его не читаем и не пишем; он показан, чтобы картина была полной.

Ваш основной инстанс никогда не закрывается, не трогается и его состояние входа никуда не копируется. Ради этого весь подход и затевался: альтернатива — закрыть приложение и подменить данные профиля на диске — перемешивает состояние аутентификации и провоцирует повторный вход на стороне сервера, во что раз за разом упираются Windows-инструменты в этой нише.

### Компромиссы

- **Диск.** Изоляция полная, поэтому профиль заново скачал бы весь свой рантайм на ~10.5 ГБ. `clone-runtime` делает это бесплатным на APFS — см. ниже. Кэши (~1.5 ГБ) по-прежнему свои у каждого профиля.
- **MCP-серверы — на профиль.** У нового профиля их нет — `-s` или `clone-config` их переносят, см. ниже.
- **`--user-data-dir` — ключ Chromium, а не документированная возможность Claude Desktop.** Так штатно запускают VS Code и большинство Electron-приложений, так что риск невелик, — но если приложение однажды начнёт жёстко фиксировать свою директорию данных, это перестанет работать.

### Где это работает

| | Запуск профилей | Аккаунт профиля (`desktop usage`) |
|---|---|---|
| **macOS** | да — `/Applications/Claude.app` или `~/Applications/` | да |
| **Windows**, установка с [claude.com/download](https://claude.com/download) | да — `%LOCALAPPDATA%\AnthropicClaude\` | пока нет — ключ лежит в DPAPI, а не в связке ключей |
| **Windows**, установка из Microsoft Store | **нет** — см. ниже | нет |
| **Linux** ([официальный пакет](https://code.claude.com/docs/en/desktop-linux), бета) | да — `claude-desktop` в `PATH` | пока нет — libsecret / kwallet |

Если приложение лежит в другом месте — неофициальная Linux-сборка, нестандартная установка — укажите путь: `CLAUDE_ACC_DESKTOP_APP=/path/to/the/app`.

**Сборка из Microsoft Store так не умеет — и не будет делать вид, что умеет.** Её исполняемый файл лежит в `WindowsApps` и запускается только через активацию Store, а это не тот способ, которым передают ключи командной строки; вдобавок пакет подменяет пути к файлам, так что дошедший ключ указывал бы не туда, куда написано. Вместо того чтобы запустить её и молча открыть ваш настоящий профиль, выдавая его за другой, `desktop` объясняет, в чём дело, и останавливается. Установщик с claude.com/download работает.

> Со слов других, нами не проверено: на Windows Cowork ищет образ своей виртуальной машины относительно `%APPDATA%`, поэтому у профиля в другом месте она может не подняться, и в любом случае одновременно работает только одна такая ВМ. Обычный чат это не затрагивает.

### Перенос MCP-серверов (`clone-config`)

MCP-серверы профиля и настройки приложения лежат в `claude_desktop_config.json` **внутри директории профиля**, поэтому у нового профиля нет ни того, ни другого. Заводить docker-MCP руками в каждом профиле надоедает быстро — это десктопный аналог [`clone-settings`](accounts.md#наследование-конфига-из-claude) для CLI-аккаунтов:

```bash
claude-acc desktop add work -s               # перенести сразу при создании, из профиля приложения
claude-acc desktop clone-config work         # или перенести в уже существующий профиль
claude-acc desktop clone-config work --from personal   # или из другого профиля
```

```
$ claude-acc desktop clone-config work
MCP-серверы и настройки скопированы из ~/Library/…/Claude/.
Скопированы только описания серверов — те, что логинятся отдельно, попросят вход и в новом профиле.
```

Существующий конфиг **сохраняется, а не затирается** — там наверняка есть серверы, добавленные руками:

```
$ claude-acc desktop clone-config work
У этого профиля уже есть claude_desktop_config.json. Заменить — с --force.
```

- **Описания, а не сессии.** MCP-сервер, который логинится сам, попросит вход и в новом профиле — так и должно быть: смысл отдельного профиля в отдельной личности.
- В файле могут лежать креды серверов, поэтому он копируется с сохранением прав (`0600` в профиле приложения) и через промежуточный файл — прерванное копирование не оставит половину конфига.

### Под каким аккаунтом каждый профиль (`desktop usage`)

`desktop list` читает только файлы, поэтому может сказать лишь, есть ли у профиля креды. `desktop usage` идёт дальше — расшифровывает токен профиля и спрашивает API: email, план и те же полосы 5ч / 7д, что [`usage`](identity.md#сколько-лимита-осталось-usage) показывает для CLI-аккаунтов:

```
$ claude-acc desktop usage
Сейчас macOS запросит пароль от связки ключей «Вход»: чтобы узнать аккаунт и расход профиля, нужно расшифровать его токен, а ключ для этого лежит в записи «Claude Safe Storage». Если отказать, не будет только этого списка.

Использование Claude Desktop:
    work  <work@company.com>  Max 20x
      5h  [██████░░░░░░░░░░░░░░]   32%  сброс через 52м
      7d  [████████░░░░░░░░░░░░]   40%  сброс через 5д 16ч
```

Узнанное кешируется, так что дальше `desktop list` показывает email, ничего не спрашивая:

```
$ claude-acc desktop list
Профили Claude Desktop:
    work  <work@company.com>  Max 20x  (выполнен вход)
    ~/Library/…/Claude/  (собственный профиль приложения)
```

**Про запрос связки ключей.** Десктопное приложение хранит токен так же, как любое приложение на Chromium в macOS: зашифрованным ключом из записи `Claude Safe Storage`, в списке доступа которой значится только само приложение. Поэтому чтение запрашивает пароль от связки ключей «Вход» — один раз, если выбрать «Разрешать всегда». Это серьёзная просьба, поэтому `desktop usage` объясняет, что собирается сделать, **до** появления диалога, а не после; больше ничто в этом инструменте эту запись не трогает. Откажете — потеряете только этот список, остальное продолжит работать.

**Часто он и не понадобится.** Если аккаунт, под которым залогинен профиль, — один из тех, которыми управляет этот инструмент, `desktop list` называет его по `.claude.json` самого аккаунта: совпадение uuid между двумя локальными файлами, без запроса к keychain и без сети:

```
$ claude-acc desktop list
Профили Claude Desktop:
    work  <work@company.com>  (выполнен вход)
    ~/Library/…/Claude/  (собственный профиль приложения)
```

Плана рядом с email тут нет: план приходит из profile API, а эта строка получена, никого ни о чём не спросив.

Когда не сработало ни то ни другое — ничего не закешировано и ни один здешний аккаунт не залогинен под этим uuid — профиль показывает сам **uuid**, он лежит открытым текстом в `config.json` профиля:

```
$ claude-acc desktop list
Профили Claude Desktop:
    work  aa6c22d5…  (выполнен вход)
```

Опознаваемой личностью это не назовёшь, но увидеть, что два профиля — это два разных аккаунта, достаточно.

> `desktop usage` есть только в Rust CLI. Расшифровка токена требует PBKDF2-HMAC-SHA1 и AES-128-CBC с явным ключом — в стоковом macOS стоит LibreSSL, у чьего `openssl` нет подкоманды `kdf`, так что шелл-скрипту понадобился бы OpenSSL из Homebrew или Python. Он показывает uuid.

### Не платить за рантайм дважды (`clone-runtime`)

Почти весь вес профиля — это компоненты, которые приложение скачивает и дальше только читает:

| Размер | |
|---|---|
| ~10 ГБ | `vm_bundles/claudevm.bundle/` — образы песочницы Cowork |
| 250 МБ | `claude-code-vm/<версия>/` |
| 220 МБ | `claude-code/<версия>/` |

Во всех профилях они одинаковые, и новый профиль качает свою копию всего этого. На APFS можно не качать: `clone-runtime` клонирует их **copy-on-write**, так что у каждого профиля получаются полностью независимые файлы, которые делят блоки с оригиналом до первой записи в любой из них.

```
$ claude-acc desktop clone-runtime work
Склонировано компонентов рантайма: 13, логически 10.5 GB, из ~/Library/…/Claude/.
Реально занято на диске: 12 KB.
```

Десять с половиной гигабайт за треть секунды и двенадцать килобайт метаданных. `--from <профиль>` клонирует из другого профиля вместо собственного профиля приложения; `--force` заменяет рантайм, который у профиля уже есть.

**Почему клон, а не общий файл.** Windows-инструменты в этой нише направляют все профили на одну директорию `vm_bundles/`. Им можно: они закрывают приложение перед переключением, поэтому файлов касается ровно один экземпляр. У нас профили работают одновременно, а две живые ВМ, пишущие в один образ, — это порча, а не экономия. У клона общего писателя нет вовсе: запись в один оставляет второй побайтово нетронутым, а место занимают только изменённые блоки.

**Что намеренно не клонируется.** В бандле песочницы перемешаны скачанное и идентичность конкретной ВМ, и ехать может только первое:

| Клонируется | Оставляется приложению |
|---|---|
| `rootfs.img`, `vmlinuz`, `initrd*` — образы | `machineIdentifier`, `macAddress`, `gvisorMacAddress`, `vmIP` — две живые ВМ с одним MAC-адресом это конфликт, а не экономия |
| `.*.origin` — из какого набора образов они взяты, чтобы приложение не качало заново | `sessiondata.img`, `efivars.fd` — собственное состояние профиля |
| `claude-code/<версия>/`, `claude-code-vm/<версия>/` — целиком: это скачанное и маркер `.verified` | `Cache/` (1.2 ГБ), `Code Cache/` (346 МБ) — живые кеши Chromium, пишутся постоянно и наполняются приложением сами |

Две оговорки, обе команда проговаривает сама:

- **Клонирование через границу файловых систем не выполняется, а отклоняется.** `cp -c` молча откатывается на настоящее копирование, когда клонировать не может, — это потратило бы 10 ГБ ради экономии 10 ГБ. Если профиль лежит не на той же ФС, что источник, команда об этом говорит и ничего не делает.
- **Примет ли приложение подложенный рантайм — не проверено.** Механика файловой системы проверена, реакция приложения — нет: никто ещё не запускал Cowork в так засеянном профиле. Если поведёт себя странно — удалите у этого профиля `vm_bundles/`, `claude-code/` и `claude-code-vm/`, и приложение скачает свои. Отчёты в любую сторону приветствуются в [#92](https://github.com/Nemo-Illusionist/claude-code-account-switcher/issues/92).

Вложений всё это не касается: файлы пользователя Cowork лежат по пути из `coworkUserFilesPath`, то есть **снаружи** профиля, и этот путь едет вместе с [`clone-config`](#перенос-mcp-серверов-clone-config) — новый профиль смотрит в ту же папку с файлами, а не в её копию.
