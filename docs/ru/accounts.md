# Аккаунты и конфигурация

[← README](../../README.ru.md) · [English](../accounts.md)

Что такое аккаунт на диске, что он наследует из `~/.claude/` и как принять
уже существующую config-папку.

## Что переключается

`CLAUDE_CONFIG_DIR` перемещает всю директорию `~/.claude/`, включая ([docs](https://code.claude.com/docs/en/settings)):

| Файл | Описание |
|---|---|
| `settings.json` | Пользовательские настройки |
| `CLAUDE.md` | Глобальная память / инструкции |
| `agents/` | Субагенты |
| `.credentials.json` | Данные авторизации |
| `projects/` | Глобальные конфиги по проектам |
| sessions, history и т.д. | Runtime-данные |

Каждый аккаунт получает свою копию всех этих файлов в `~/.claude-switch/accounts/<name>/`.

### Дефолтная модель на аккаунт

Поскольку у каждого аккаунта свой `settings.json`, дефолтная модель на аккаунт работает «из коробки» — без отдельного флага или конфига. Пропишите ключ [`model`](https://code.claude.com/docs/en/settings) Claude Code в settings.json нужного аккаунта:

```bash
# например, Opus на work и модель полегче на personal
echo '{ "model": "opus" }' > ~/.claude-switch/accounts/work/settings.json
```

Теперь любой `claude`, запущенный под аккаунтом `work`, стартует с этой моделью. (Тулзы, которые шарят один `settings.json` через симлинк между аккаунтами, так не умеют без отдельного механизма — здесь это просто следствие изолированного config-dir.)

## Наследование конфига из `~/.claude/`

Свежий `claude-acc add work` создаёт **пустую** директорию — без `settings.json`, без `CLAUDE.md`, без кастомных агентов. Чтобы новый аккаунт стартовал с тем же setup'ом что и ваш стандартный `~/.claude/`, используйте флаг `-s` / `--seed` при создании или `clone-settings` ретроактивно:

```bash
claude-acc add -s work               # засеять при создании
claude-acc clone-settings work       # засеять существующий аккаунт
```

Обе команды копируют curated set файлов из `~/.claude/`:

**Копируются** (конфигурация / персонализация):
- `settings.json` (env vars, permissions, ссылки на хуки, statusline, plugins, language)
- `CLAUDE.md` (глобальная память)
- `agents/`, `commands/`, `output-styles/`, `skills/` (кастомные ассеты)
- `plugins/` — установленные плагины и marketplace'ы, из которых они пришли

**Не копируются** (per-account state — иначе ломается изоляция):
- `.credentials.json` (токен — повторно получается через `claude auth login`)
- `settings.local.json` (per-machine локальные оверрайды)
- `projects/`, `todos/`, `statsig/` (сессии, runtime state, телеметрия)
- `hooks/` (settings.json ссылается на них по абсолютным путям; копировать = плодить файлы без пользы)
- `.account-info.json` (наш doctor-кэш)

### Что происходит с плагинами

Claude Code держит реестр плагинов **отдельно для каждого конфиг-каталога**,
поэтому новый аккаунт стартует без единого плагина — из-за этого их и
переносим, а не оставляем за бортом.

Но простым копированием не обойтись: реестр хранит абсолютные пути в тот
конфиг-каталог, для которого он написан. Копия как есть оставила бы новый
аккаунт грузить кэш плагинов старого — работает по случайности и ломается,
как только тот аккаунт удалят. Поэтому `installPath` и `installLocation`
переписываются на новый аккаунт. Marketplace, который лежит вне
конфиг-каталога — например, закоммиченный в проект, — сохраняет свой путь
ровно как был; ради этого переписывание идёт по этим двум полям и по
префиксу, а не текстовой заменой.

Аккаунт, где плагины уже установлены, не трогается. Seed — это не слияние,
и то, что вы там поставили, остаётся вашим.

Существующие файлы в target'е не перезаписываются — `clone-settings` это одноразовый seed, не sync.

### Фичи, которые включаются отдельно в каждом аккаунте

Seed копирует файлы. Он намеренно не трогает `.claude.json` — тот самый файл, где лежит ещё и `oauthAccount` и где неверное значение приписало бы аккаунту чужую личность. Несколько пользовательских фич записываются именно туда, поэтому в новом аккаунте они всегда начинают с нуля.

**Claude in Chrome** — та, с которой вы столкнётесь вероятнее всего. Claude Code подключает этот MCP-сервер отдельно для каждой config-папки, по ключу `claudeInChromeDefaultEnabled`. Новый аккаунт никогда не отвечал «да», поэтому браузерные инструменты там просто отсутствуют — и это читается как «на машине нет расширения», а не «в этом аккаунте его не включали». Выполните `/chrome` один раз внутри аккаунта, и настройка закрепится:

```bash
claude-acc run work        # затем один раз /chrome
```

`doctor` сообщает об этом, когда видит расхождение: расширение машине знакомо, а в каком-то аккаунте переключатель выключен:

```
$ claude-acc doctor
Проверка 1 аккаунт(ов):
  ? work  нет токена (запустите: claude-acc login work)

Claude in Chrome выключен в: work. Claude Code хранит этот переключатель отдельно для каждой config-папки, поэтому браузерные инструменты там не появятся, пока вы один раз не выполните `/chrome` внутри этого аккаунта.
0 из 1 аккаунтов в порядке.
```

Если ни один аккаунт здесь не встречал расширение, `doctor` молчит: выключено на машине, где его не ставили, — это правильное состояние, а не находка. И на код возврата это никогда не влияет: браузерная фича — не чужая личность, а код возврата означает только её.

Само расширение ставится один раз на браузер, а native messaging host, через который оно общается, вообще не привязан к аккаунту и обслуживает любой. Отдельный для config-папки только переключатель.

**Computer use — случай другой, и здесь он не чинится.** Claude Code гейтит его по подписке: `max` или `pro`. Аккаунту на плане `team` или `enterprise` он недоступен — одинаково и в управляемом аккаунте, и в обычном `~/.claude/`. Этот инструмент на такое не влияет, поэтому `doctor` про него ничего не говорит.

## Отдельные настройки для проектов

Каждый аккаунт получает свою папку `~/.claude-switch/accounts/<name>/`, которая используется как `CLAUDE_CONFIG_DIR`. Это значит, что у каждого аккаунта свои `settings.json`, credentials и история проектов.

Это можно использовать для разных настроек на разных проектах — даже под одной авторизацией. Просто создайте несколько аккаунтов и войдите с теми же данными:

```bash
# Общий рабочий аккаунт с дефолтными настройками
claude-acc add work
cd ~/work
claude-acc link work

# Тот же логин, но со своими настройками для конкретного проекта
claude-acc add work-ml
cd ~/work/ml-project
claude-acc link work-ml

# Теперь можно настраивать settings независимо:
# ~/.claude-switch/accounts/work/settings.json       — для всех рабочих проектов
# ~/.claude-switch/accounts/work-ml/settings.json     — только для ml-project
```

> Примечание: `claude-acc add` запускает `claude login`, поэтому нужно будет залогиниться повторно (тот же аккаунт, просто новая папка конфига).

## Импорт существующей config-папки

Уже держите несколько аккаунтов вручную — отдельные `~/.claude-work` / `~/.claude-personal` через алиасы с `CLAUDE_CONFIG_DIR`? `import` усыновляет такую папку в управляемый аккаунт **без повторного логина**:

```bash
claude-acc import work ~/.claude-work          # скопировать папку
claude-acc import work ~/.claude-work --move    # …или перенести
```

Команда копирует (или переносит) директорию в `~/.claude-switch/accounts/<имя>/`, затем проверяет личность и печатает email, к которому она привязана.

Главная тонкость, которую он берёт на себя: на macOS Claude Code хранит OAuth-токен в Keychain под ключом, выведенным из **абсолютного пути config-папки**, поэтому простое копирование «осиротило» бы токен на новом месте. `import` перепривязывает запись Keychain к новому пути — auth продолжает работать, `claude login` не нужен. (Если токен лежит в plaintext `.credentials.json`, он просто едет вместе с папкой.) Если ни того, ни другого нет — `import` всё равно отработает и подскажет запустить `claude-acc login <имя>`.
